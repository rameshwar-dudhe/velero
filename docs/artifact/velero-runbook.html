Why the negative test is the valuable one

T22 deliberately puts a PVC on the wrong StorageClass and asserts Velero still silently skips it. If that test ever starts failing, that is news rather than a bug — Velero's behaviour changed and the storage guidance in the docs needs revisiting. A test suite that only proves the happy path cannot tell you that.

Found by actually running the teardown

Deleting Velero's CRDs by hand deadlocks forever.

Velero puts finalizers on its own objects (restores.velero.io/external-resources-finalizer), and only the Velero controller removes them — which helm uninstall already deleted. Deleting the CRDs then makes Kubernetes wait forever on custom resources nothing is left to finalize, and kubectl delete crd --wait hangs.

the symptomstuck
kubectl get crd | grep velero.io
restores.velero.io    2026-08-14T19:16:06Z   # Terminating, forever

Fix: strip the finalizers before deleting the CRDs. uninstall-local.sh now does this for every Velero resource type and deletes CRDs with --wait=false plus a bounded timeout, so it cannot hang again. This is the reason to use the script rather than hand-rolling a teardown.

Architecture

Two facts explain every failure mode: velero backs up API objects, node-agent backs up file data. They write to the same bucket over two independent paths.

The trap that will bite you

Encountered on the first attempt

A backup can report Completed and contain none of your data.

The first backup here said Completed, 24 items. The PVC contents were never captured. Restoring it would have produced a healthy-looking pod with an empty volume — the worst failure mode there is, because it looks like success.

velero backup logs demo-backup-1buried in the log
level=warning msg="Volume data in pod velero-demo/demo-app-… is a hostPath
volume which is not supported for pod volume backup, skipping"

local-path-provisioner provisions PVs with a hostPath volume source, and Velero's file-system backup refuses those outright. The Kubernetes objects were saved; the data was not.

The cheapest signal

The WARNINGS column. Both backups below are Completed; only one contains volume data.

NAMESTATUSERRORSWARNINGSReality
demo-backup-1 Completed 0 1 no volume data
demo-backup-2 Completed 0 0 volume backed up

Always verify this way

the check that actually mattersbash
# ZERO PodVolumeBackups = no volume data in that backup, full stop.
kubectl -n velero get podvolumebackups -l velero.io/backup-name=<BACKUP>

# Or read it off the backup itself:
velero backup describe <BACKUP> --details | sed -n '/Backup Volumes/,$p'

The fix on this cluster: put anything whose data must survive on the local-static StorageClass, not the default local-path. On a cloud cluster the trap does not apply — use CSI snapshots.

Why it is configured this way

The cluster was surveyed before anything was installed. Three findings dictated every choice — this is not a copied tutorial config.

FindingConsequenceSetting
No StorageClass at all — kubectl get sc returned nothing, and 4 PVCs sat Pending MinIO could not get a volume. Installed local-path-provisioner as the default; it also unblocked the stuck monitoring PVCs local-path (default)
No CSI snapshot support — no snapshot.storage.k8s.io CRDs, only Calico's ephemeral driver Volume data must be copied over the filesystem. A VolumeSnapshotLocation would never validate snapshotsEnabled: false
defaultVolumesToFsBackup: true
Control-plane node carries NoSchedule The DaemonSet would skip that node, silently losing volume data for any pod on it nodeAgent.tolerations
CLI runs off-cluster, cannot resolve cluster DNS velero backup logs failed even on successful backups — the CLI reads straight from object storage config.publicUrl
Helm values land in release history in etcd, in plaintext No credential appears in any values file; Secrets are created out of band credentials.existingSecret

Retention

Never remove a backup with kubectl delete backup — that orphans its data in the bucket forever with nothing referencing it. Always velero backup delete <name> --confirm.

Web UI

Velero ships no official UI — it is CLI and CRDs by design. The most actively maintained community dashboard, otwld/velero-ui, is deployed at http://192.168.56.134:30902. Two of its chart defaults are dangerous and were changed.

Chart default 1 · privilege escalation

rbac.clusterAdministrator: true binds cluster-admin.

The chart's default binds Kubernetes' built-in cluster-admin role to the UI's ServiceAccount. Combined with its other default of admin/admin, a stock install hands full cluster control to anyone who can reach the Service.

Set to false, which switches to the chart's own purpose-built ClusterRole: velero.io/*, namespaces get/list, and health URLs — nothing else.

verify what it actually boundbash
kubectl get clusterrolebinding velero-ui -o jsonpath='{.roleRef.name}'
velero-ui   # ✓ not cluster-admin
Chart default 2 · forgeable sessions

The JWT passphrase cannot be set through the chart at all.

AUTH_SECRET_PASSPHRASE defaults to the published string “this is not a secret passphrase”. Left alone, anyone can forge a valid session token and skip the login entirely.

The chart creates a Secret from secretPassPhrase.value but never references it in the Deployment — so that value silently does nothing. Both the password and the passphrase are injected directly instead, from a Secret built by scripts/gen-ui-credentials.sh.

What no dashboard can tell you

The UI reports Velero's own state faithfully — and inherits its blind spot. A backup that silently skipped your volume data still shows as Completed in every dashboard. That only surfaces in velero backup logs and the PodVolumeBackup count. Green in a UI is not evidence your data is recoverable; keep running the verify script.

Also worth knowing: UI access is effectively read access to Secrets in the velero namespace — which includes your object-storage keys. That is inherent to showing backup detail, not something RBAC can remove. And it is plain HTTP, so the password and every JWT cross the LAN in the clear.

The one caveat

Read before trusting this with real data

Backups currently live on the disk of the cluster they protect.

MinIO stores every backup on k8s-w-0's local disk, inside the cluster being backed up. That protects you against an accidental kubectl delete namespace, a bad deploy, or a lost PVC — genuinely useful, and the Velero configuration itself is production-shaped.

It does not protect against losing that disk, the node, or the cluster. A backup on the same disk as the thing it protects is an undo button, not disaster recovery.

The fix is four lines — point the BackupStorageLocation at external object storage with values-s3-generic.yaml, and enable bucket versioning plus object lock. Full checklist in docs/06-production-notes.md.

Also worth doing before production

  • MinIO serves plain HTTP — S3 keys cross the LAN in the clear. Add TLS, and remove or firewall the NodePort.
  • Swap MinIO root credentials for a user scoped to the velero bucket.
  • Alert on velero_backup_last_successful_timestamp going stale — that catches a silently broken schedule, which no failure counter will.
  • Replace the static PV pool with a real CSI driver (Longhorn, OpenEBS LVM/ZFS, Ceph/Rook) for dynamic provisioning and genuine snapshots.
  • Rehearse restores on a schedule. An untested backup is a hypothesis.
